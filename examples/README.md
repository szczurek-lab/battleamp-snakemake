# BattleAMP web API — reference examples

These files are the contract for the web front end. Every one was generated by
`python scripts/generate_api_examples.py` from **real model predictions**, so
they show exactly what the API returns — no invented numbers.

## The API

```python
import battleamp

battleamp.list_models()                                  # -> JSON str
battleamp.validate(fasta_text, models=None)              # -> JSON str
battleamp.score(fasta_text, models=None, unit="ug/ml")   # -> JSON str
battleamp.to_tsv(result_json)                            # -> TSV str
```

Everything in, everything out is a string. The web layer never touches the
filesystem and never needs pandas.

## ⚠️ Where each function may be called from

| Function | Typical time | Call from |
|---|---|---|
| `list_models()` | ~10 ms | request handler ✅ |
| `validate()` | ~10 ms | request handler ✅ |
| `score()` | **minutes to hours** | **background worker only** ❌ |

`score()` launches Snakemake, which may build conda environments and load model
weights onto a GPU. Calling it inside an HTTP request handler will blow through
any normal gateway timeout. Run it from a task queue (Celery, RQ, or a plain
subprocess) and have the browser poll a job endpoint.

## The score response

```jsonc
{
  "status": "ok" | "partial" | "failed",
  "dataset": "upload_<hash>",     // cache key, see below
  "unit": "ug/ml",
  "requested_models": ["example-model", "apex", ...],

  "columns": [                    // one per model variant, in table order
    {"name": "apex-ecoli_MIC_ugml", "variant": "apex-ecoli", "model": "apex",
     "kind": "mic", "unit": "ug/ml", "length_min": 1, "length_max": 50}
  ],

  "rows": [                       // one per peptide
    {"id": "seq_001;seq_014", "sequence": "GIGKFLHSAKK...",
     "apex-ecoli_MIC_ugml": 268.098, "mbc-attention_MIC_ugml": null}
  ],

  "input":  { "n_records": 25, "n_sequences": 20, "rejected": [...] },
  "models": { "<variant>": {"status": "ok"|"partial"|"failed", ...} },

  "messages":    [ ... ],   // SHOW THESE TO THE USER
  "diagnostics": { ... }    // DO NOT show these to the user
}
```

### Column naming

`{variant}_prob` for classifiers, `{variant}_MIC_{unit}` for regressors.

The prefix is the **variant**, not the model. One model can contribute several
columns: `apex` alone produces six (`apex-ecoli`, `apex-saureus`, …) from a
single run, and `sensexamp` produces one classifier plus two regressors.
Variant names are globally unique, so columns never collide. Use the `columns`
array to label the UI rather than parsing column names.

### Empty cells

`null` in JSON, empty in TSV. There are three reasons, and `models[variant]`
tells you which:

| `status` | Meaning | What to tell the user |
|---|---|---|
| `ok` | Model ran, scored everything | — |
| `partial` | Model ran, some peptides outside its length range | "13 of your peptides are outside this model's 6–25 aa range" |
| `failed` | Model did not produce output | "This model could not be run; the others are unaffected" |

A peptide rejected before any model ran (bad residue, D-amino acid, gap) never
appears in `rows` at all — it is listed in `input.rejected` with a reason.

### messages vs diagnostics

- **`messages`** — short, already human-readable, safe to render verbatim. Each
  has `severity` (`error`/`warning`/`info`) and `kind` (`input`/`coverage`/
  `model`/`run`) so you can group or filter them.
- **`diagnostics`** — Snakemake log paths, log tails, the exact command line.
  These contain absolute server paths, conda environment paths and CUDA
  warnings. Keep them for operators; never put them in front of an end user.

Snakemake is run with `keep-going`, so **a non-zero Snakemake exit code is
normal** whenever any single model fails. Judge the run by `status` and by
`models[*].status`, not by `diagnostics.snakemake.returncode`.

## Caching

The dataset name is `upload_<sha1-of-cleaned-sequences>`, not the uploaded
filename. This matters:

- Two users who upload different files both named `peptides.fasta` do **not**
  collide.
- Two users who submit identical peptides **share** the computation.
- Running 3 models today and 5 tomorrow re-runs only the 2 new ones; the
  response still contains exactly the models asked for in that call.

Predictions are cached under `results/inference/{variant}/{dataset}/`. Nothing
is ever overwritten, because each response is assembled fresh from the cache.

## Suggested request flow

1. User pastes or uploads FASTA → call `validate()` → show rejections and
   per-model coverage immediately.
2. User picks models and a unit (`list_models()` gives both lists).
3. Enqueue a job that calls `score()`; return a job id.
4. Poll until done; render `rows`/`columns` as a table, `messages` as banners,
   and offer `to_tsv()` as a download.

## Server setup

`score()` runs Snakemake, which runs `conda`. Neither is on the PATH of a
typical service worker, so the worker environment must set:

```bash
export BATTLEAMP_SNAKEMAKE=$HOME/.venvs/battleamp-snakemake/bin/snakemake
source $HOME/miniforge3/etc/profile.d/conda.sh
export BATTLEAMP_PROFILE=slurm/     # or profile/ to run on the local machine
```

If they are missing, `score()` still returns a well-formed response whose
`messages` say Snakemake could not be found — it does not crash — but every
model will be reported as failed.
